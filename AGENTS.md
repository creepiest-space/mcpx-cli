# MCPX Contributor Guide

## Scope

- These instructions apply to the entire repository unless a deeper `AGENTS.md` overrides them.
- Keep source code, comments, tests, CLI messages, and documentation in English.
- Treat `tmp/mcpx-david` and `tmp/mcpx-thoroc` as read-only reference implementations. Do not
  format, refactor, or otherwise modify them.

## Repository Structure

- This is a Bun and Turborepo TypeScript monorepo.
- `packages/core` owns canonical Zod schemas, config persistence, provider contracts, detection,
  synchronization, and filesystem ports. It must not depend on provider formats or terminal UI.
- `packages/providers` owns provider-specific JSON, JSONC, and TOML adapters and the default
  provider registry. It depends on `@creepiest-space/mcpx-core`.
- `apps/cli` owns Citty routing, commands, output, dependency composition, and the Clack wizard. It
  depends on both packages.
- Preserve this dependency direction: `apps/cli -> packages/providers -> packages/core` and
  `apps/cli -> packages/core`.

## Development Commands

- Install dependencies with `bun install`.
- Format files with `bun run format`; verify formatting with `bun run format:check`.
- Run Oxlint with `bun run lint`; use `bun run lint:fix` only for safe mechanical fixes.
- Run the complete static quality gate with `bun run check`.
- Run all tests with `bun run test` and build all packages with `bun run build`.
- Create Conventional Commit messages interactively with `bun run commit`; Lefthook applies Oxlint
  and Oxfmt fixes to staged files and Commitlint validates commit messages.
- Run a focused test from the repository root with, for example,
  `bun test apps/cli/test/commands.test.ts`.

Before handing off code changes, run `bun run check` and the relevant tests. Run the full test and
build commands when changing public contracts, provider adapters, CLI wiring, or tooling.

## TypeScript and Formatting

- Use strict TypeScript and ESM. Include `.ts` extensions in relative imports.
- Let Oxfmt define layout; do not hand-format against `.oxfmtrc.json`.
- Keep Oxlint warning-free. Prefer fixing a diagnostic to disabling a rule; narrowly explain any
  necessary disable directive.
- Validate external and persisted data at boundaries with the canonical Zod schemas. Do not replace
  validated types with unchecked casts.
- Keep operations asynchronous through the `FileSystem` port outside CLI infrastructure.

## Canonical Configuration

- Project state lives at `.agents/mcp.json`; global state lives at `~/.agents/mcp.json`.
- The canonical format is version `1` and uses discriminated `stdio` and `http` server definitions
  with an explicit `enabled` flag.
- Use `ConfigStore` for canonical reads and writes so validation and normalization remain active.
- Pass scope, home directory, environment, registry, filesystem, and output through the existing
  context or option objects. Tests must not read from or write to the real user home directory.

## Provider Safety

- Register every new provider in `createProviderRegistry` and add round-trip, path, and preservation
  tests.
- Respect project/global capabilities and candidate paths through the helpers exported by core.
- Provider generation must preserve unrelated settings in shared tool configuration files.
- Never delete an entire shared provider file merely to remove MCPX-managed data. Remove only the
  managed section, or delete a file only when it is known to be exclusively generated by MCPX.
- Keep provider-specific mappings inside adapters; core must remain format-agnostic.

## CLI and Wizard

- Keep Citty definitions in `apps/cli/src/commands/index.ts` and command behavior in separate command
  modules.
- Use `CliContext` dependencies rather than constructing registries, filesystems, or output objects
  inside commands.
- Keep Clack prompt code in the CLI package. Non-interactive messages should go through `Output`.
- Preserve both project and global scopes and support `--dir`, `--scope`, and `--verbose` consistently.
- Treat cancellation, back navigation, sync errors, import conflicts, and process exit status as
  explicit behaviors and cover them with tests.

## Testing Expectations

- Core changes require unit tests using an in-memory `FileSystem` and fake providers where useful.
- Provider changes require parsing/generation round trips and tests proving unrelated settings are
  preserved.
- Command changes require success, validation-error, and missing-config coverage.
- Wizard changes require cancellation and conditional-navigation coverage; do not rely only on manual
  terminal testing.
